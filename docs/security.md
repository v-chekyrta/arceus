# Security

## The screen

Anything people or CI wrote is read by a classifier before the agent gets it: the ticket when the task starts, an answer to the agent's question, the text of a `/continue`, every review round (MR threads, CI logs, ticket comments) and the code reviewer's brief. The runner's own messages (a resume after a reboot, a nudge after a stall, a bare `/continue`) are not screened. `Engine.dispatch` and `Engine.send` refuse a text without clearance, so a new path to the agent cannot skip the screen by accident.

- **The classifier** is `claude -p` with no tools, MCP servers, settings or session, in an empty temporary folder, with the policy as its system prompt and the message as a JSON field. It answers `allow`, `review` or `block` with categories and a short reason, checked against a strict schema. It uses the agent's Claude sign-in, so no new provider sees the client's text. Codex is not used: its sandbox still lets it read files. The policy is in [`screening.py`](../runner/src/arceus_runner/screening.py), the model in `security.model`.
- **What it holds:** sending code, data or credentials outside the project; collecting everything the agent can reach; personal data; reading or exposing secrets; irreversible damage; weakening the agent's or the server's controls; backdoors; claimed authority ("the CTO approved"); instructions aimed at the agent instead of the task, hidden or encoded ones included. Ordinary and security work pass: fixing a vulnerability, a test with an attack string, a CI failure. Hidden Unicode (tag characters, bidi controls) and texts over 100,000 characters are held whatever the model says.
- **Only `allow` lets a text through.** `review` and `block` move the task to `security_hold`, with one comment on the ticket that mentions `security.reviewers`, says what was found (never the text) and gives a code. A reviewer answers `/security-allow <code>` to send exactly that text or `/security-reject <code>` to drop it and fail the task. Someone whose words are in the text cannot decide on it (for a ticket: the tag's author, the reporter and the last editor). An approval covers that hold only; a changed text is screened again, and a rejected one is refused from then on in any task. `/continue` does not lift a hold. A held task blocks nothing else.
- **When the classifier does not answer** (a limit, a sign-in, a timeout), nothing is sent: the item is retried on the next tick, `screening_unavailable` is logged and the `security.screening` health check fails, which stops new tasks. A text it fails on three times goes to a reviewer. A refusal to classify counts as `review`.
- **Files from the ticket** (YouTrack; a tracker without `reads_attachments` gives text only) are screened with the text they come with: images (PNG, JPEG, GIF, WebP, up to 12 MB) and PDFs (up to 16 MB) as the model sees them, text files (up to 512 KB) as text, at most 20 files and 48 MB per delivery. Text files that would take the message past the screen's 100,000 characters are left out, longest first, with the reason. A comment with only a file in it counts like one with text. The runner downloads them with its own token into memory and copies them into `.arceus/ticket/<KEY>/` (with `materials.json`) only after clearance; the text tells the agent where each file is and which one each in-text reference means. Other kinds (archives, Word, Figma, video), files over a limit or ones the bot may not read are not given, and the text says why. A replaced file is screened again, and whoever attached a file cannot release it. Large PDFs are read a few pages at a time with `pdftoppm` (`packages` phase). Many files go over several classifier calls, each with the whole text; the strictest verdict counts, and a file the model reports it could not see holds the text for a person. YouTrack's signed download addresses never reach the agent, the manifest or the logs. How files are batched for the model is in `screening.py` (`CALL_FILE_BYTES`) and [`materials.py`](../runner/src/arceus_runner/materials.py).
- **Logs:** `events.jsonl` gets the verdict, categories, model and a 12-character code of the text (`screened`, `security_hold`, `security_released`, `security_rejected`), never the text or the reason. The database keeps verdicts and holds, not texts.
- **Checking the policy on the real model:** `ARCEUS_SCREEN_LIVE=1 pytest tests/test_screen_live.py` (one Claude call per case: Russian and English attacks and ordinary tasks, images, PDFs and text files; `ARCEUS_SCREEN_MODEL` picks the model). Run it after changing the policy or `security.model`.

The screen lowers the risk without removing it: a classifier can be talked past, and instructions can also reach the agent from repository files, web pages or tool output. Then what protects the data is what the agent can actually reach on the VM.

## Trust boundary

Claude's workers run as the same user as the runner, which has passwordless sudo and the `docker` group, so the agent can technically read the runner's tokens and do anything on the VM. Bulava's server-profile denies (reading `~/arceus/data/*`, `~/.ssh`, `~/.git-credentials`, the Claude and Codex credentials; `glab`, `gh`, `git push`) and the root-owned `/opt/*` protect against accidents, not intent. The isolation boundary is the VM itself. That is why the bots' tokens have minimal rights and outbound traffic is to be put on an allowlist. Protecting the default branch is the team's decision: where a Developer may push, merge or force-push it, so may anything that reads the bot's token. `setup/checks/gitlab-protection.py` shows those repositories as warnings and fails only where the bot cannot publish its task branches.
