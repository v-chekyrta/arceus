# Reviews

Besides Codex there is one more review: a code review a person asks for on the ticket.

## Codex alone before the merge request

Codex is the only reviewer before a merge request is opened. Bulava 1.19.2 removed the separate Claude code and security checks that ran before it, and with them `bulava.claude_checks`. A `config.yaml` that still has that block is refused by name: delete the block. On a server Codex reviews with a team of three (contract, security, state); `doctor` shows its members in `bulava.engine.review_team`. An engine that still says it runs the Claude checks is older than the pinned one, and `doctor` warns about it in `bulava.engine.claude_checks`: run `sudo ./setup.sh`. The incoming text screen (docs/security.md) does not change.

**Start handshake.** The engine rolls a start back when the new session's hooks do not confirm it in time (5 s in the engine), which fails the ticket. A cold Claude on a busy machine is slower, so the runner passes `bulava.start_handshake_wait` (30 s by default, 5 s–2 m).

## Code review on request

Off by default (`review_agent.enabled: false`); then `/review` is an ordinary comment to the agent. With it on, someone in `allowed_users` writes on a ticket in Code Review a comment starting with `/review` (`review_agent.command`), or one that mentions the tracker bot and then says `review` (`@agent-runner review, mostly the migration`). What follows is passed on as what to look at.

**The request.** Recognised before any other handler reads the comment, so it never reaches the agent that wrote the code. Written on an MR it starts nothing: reviews are asked for on the ticket, where the allowlist applies. Someone not on the list, a ticket outside Code Review, a review already under way, or `max_per_ticket` reached get a one-line answer and no review; refused requests do not count towards the limit. A taken request gets 👀 from the bot at once (journaled, so a tracker outage delays it but never doubles it). With Slack set up, the channel hears when a review starts and its result per MR.

**The run.** The review is a Bulava task of its own, `<KEY>.review-<n>`, never a follow-up of the author's session. Its text is the ticket whole (description and every comment, through the security screen; a text too long for the screen is held for a person, never shortened) plus the open MRs and what people wrote on them (every note but the host's system notes, the runner's and the review's own), oldest first, since a decision made on an MR narrows the ticket as much as one on the ticket. Each MR's repository is checked out at the host's commit on a local branch `arceus-review/<KEY>-<n>`, readable but not writable: the reviewer builds and runs the tests, it changes nothing and asks nobody. Its verdict goes to `.arceus/reviews/<KEY>/<id>.json`: per MR, whether it meets the ticket, build and tests as seen, whether it looked at what people see, blockers, findings of fit, suggestions (at most `max_suggestions`) and changes for a person. The reviewer is told not to add requirements: the ticket, its acceptance criteria and design notes, as people's comments changed them, are the whole of what it judges against, and a decision a person wrote down is never one to undo or to raise again as a suggestion. Each blocker names what it breaks (a requirement or behaviour that works on the target branch) and how ordinary use reaches it (`breaks`, `reached_by`). Hardening nobody asked for, input nothing in the system produces and a race that needs several unlikely things at once are suggestions.

**The project's rules and fit.** How a project wants its code is not in the review's brief: the reviewer reads it from the project's notes and from each changed repository's CLAUDE.md and AGENTS.md (at the root and in the folders of the changed files), judging an edited rule by its version on the target branch, and the ticket or a person's decision wins over a rule. Before any finding of fit it writes `scope` into the verdict: what the change does, group by group, each with the line of the ticket or of a comment that asks for it, the asked-for change that needs it, or "nobody" (settling a question people left open or reading a criterion more widely than its words counts as nobody); and each new definition with the closest existing code of the same kind. Findings of fit follow from that list, the largest first. A finding of fit (`severity: fit`) is what people who keep the code send back although nothing is broken, and it names what it stands on in `basis` and `evidence`: a written rule it breaks, quoted (`rule`); existing code that already does the same job, or a second place doing that job left behind, or mocks, fixtures or screenshot baselines left at the old version (`existing`, with `file:line`); code that does nothing or goes the long way round, with the plain form (`needless`); a change no line of the ticket or of a comment asks for, a change to shared code wider than the ticket needs included (`unasked`). It asks to remove or align, never to add. It counts only when the runner finds what it stands on: a line the change adds or changes (or within three lines of one; a deleted file's old lines count), and by its basis the whole quoted rule (four words or more) in the project's notes or in the source it names on the target branch: a document, or a CLAUDE.md or AGENTS.md at the root or in a folder above the changed file (a rule the change writes or weakens itself does not count, nor a source that is not there); a line of a text file in the reviewed or the target commit that holds a name the evidence gives; every entry of `scope` about the same thing (the same `name`, or the same file) saying nobody asked for it, or for needless code the plain form in words with something in the code named. Otherwise it is a suggestion. A preference neither the rules nor the code around it share is not a finding.

**What people see.** When the change alters anything a person sees or operates, the reviewer runs the repository's end-to-end, visual and accessibility suites for it and opens the changed screens in a browser, in the states the ticket names, at a phone and a desktop width or the project's own. It reports `ui`: `checked`, `not_run` (it could not look, and says why) or `none` (nothing a person sees changed). A verdict without `ui` is not a pass. A run that asks a question, passes `review_agent.timeout` or leaves no readable verdict ends as "could not be confirmed". On a server Codex checks the reviewer's closing report, and only a report it passes can be approved. It judges the report by the review's own criteria (`code_review.REPORT_CRITERIA`, given to the reviewer too), not by the server's rule about data changes: each verdict follows from what was checked, each claim names the command or file behind it, nothing is claimed beyond the checks, and the test databases and containers the checks made are expected, so naming where they ran is enough. It gets up to 5 rounds. When Codex still disputes the report at that limit, the runner gives the reviewer its objections back once, to correct the report or, if they show the verdict is wrong, the verdict. A report it then passes counts like any other; one it still disputes ends as "could not be confirmed", with no approval and nothing sent to the author, blockers included, since the dispute is about the review, not the code. It holds the shared workspace like a task; afterwards the runner stashes what it left, puts every repository back and deletes the review branch.

**What the runner approves.** The model advises; the runner decides. An MR is approved only when all of this holds:

- the reviewer found it ready: requirements met, build passed, tests passed (or the repository has none), no blocker, and what people see either looked at or unchanged (`ui: not_run` makes it "could not confirm", naming what was not looked at);
- no finding of fit, while the ticket has fix rounds left (below);
- the build and tests satisfy the repository's rule in `review_agent.repos`, matched by path in the group (`services/api`, or a pattern such as `services/*`; the exact path wins, then the first pattern):
  - `build: none` / `tests: none`: not needed for this repository; what the reviewer did not run stops nothing, but a failure it saw still does;
  - `ci_build_jobs` / `ci_test_jobs` (`*` and `?` allowed): what the reviewer could not run itself counts as passed when, in the CI run of the reviewed commit, at least one job matches and every match succeeded;
  - no rule: both as the reviewer ran them;
- tests that also fail on the target branch without the change are reported as `failed_before` and ask for nothing;
- the host's newest CI run is for the reviewed commit and passed (`require_green_ci`; a running one is waited for);
- the MR still points at that commit and target branch, the ticket is still in Code Review with the text the review read, and nobody has commented on the MRs since the review started.

Then the approver approves exactly that commit, with a note "ready to merge" that says the review found nothing that has to change before merge; it does not say a person need not look. The note also names, for a person to look at before merge:

- changed files that match `attention_paths` (by default auth, permissions, crypto, `.env`; ordinary tests and docs are left out);
- what the reviewer says a person has to decide: a security boundary changed in substance, a CI check removed or weakened, wider privileges or exposure, a migration that drops or rewrites existing data, behaviour other systems rely on changed beyond the ticket, a hard-to-reverse product decision the ticket left open.

Findings of fit the runner did not send back (people wrote the code, `fix_rounds` is 0 or used up, the review could not confirm the MR) are listed under "Does not fit the project", with why they stayed there.

What only the people who release it need to know (an environment variable, a requested runtime upgrade, a new dependency, an additive schema change) goes under "For whoever deploys it" and calls nobody. Files under `review_hint_paths` (CI, Docker, Makefile, dependencies, settings, migrations) are pointed out to the reviewer to read with care. Otherwise the note says what has to change or why the review could not confirm it, and an earlier approval is taken back. An approval is also taken back, once and with a reason on the MR, when the MR gets new commits, changes target, or the ticket's description or files change (a comment does not). A final review stands for the same commits only against the same target commit, under the same `review_agent.repos` rules and the same rules of judging (`code_review.RULES`); a result an older runner decided and did not finish posting is decided again before anything is approved. The ticket gets one summary with a line per MR.

**What the ticket says.** The comment on the ticket gives each MR's outcome and the reviewer's summary; each finding and suggestion is on its MR's note. A reviewer that is unsure writes the one decision people have to make as a question (`question`), with two to four answers to pick from, each saying what the code would then need (`options`), beside why it asks (`unsure_because`). The ticket's comment then starts with the question, the answers and why, and says how to answer: a comment on the ticket (not `/review`), which goes to the agent. The agent gets that comment alone, not the question, so the ticket asks for the decision in full rather than a yes or no, with the question and its first answer as an example. Once the agent has answered and the ticket is back in Code Review, someone writes `/review` again, also when the agent changed nothing and also after a fix round's own re-review: that one may run before the answer, and a review asked for after a new comment reads the commits anew. On code people wrote, settle it with its author. The MR's note shows the question above why it was not confirmed and also says to answer on the ticket before asking for the review again. Without a `question`, the reason is the question. A review run that did not finish as asked (the reviewer stopped to ask, its report is disputed) asks nobody its question and its summary is left out: both may be half-formed, so the ticket says what got in the way and to repeat the review.

**A merge the review did not let through.** When an MR a review judged is merged, the runner compares the merge with the newest finished review of it. If that review asked for changes (findings of fit alone do not count), or the MR was merged at commits the review never read, the ticket gets one comment that says which, with the blockers the review found when it asked for changes (an unconfirmed review's findings are left out), and Slack is told (`review_merged_unchecked` in the event log). A merge at the reviewed commit, or at a rebase or squash GitLab records with the same patch id, is left alone; on a GitLab that keeps no patch ids any other head counts as unreviewed. A review that could not confirm the MR, then merged as it was, is the people's decision and is not reported. MRs no review judged are not looked at, and a merge while a review runs is left to that review's own result. The comment is posted once per MR, also after a tracker outage or a restart. A judged MR is followed until it is merged or closed even after the runner lets go of its ticket (moved back to In Progress for the fixes, or the task ended), so a merge weeks later is still checked.

**The approver.** GitLab does not let the bot approve MRs it opened, so approvals come from a second account, `code_host.approver`, with its own token in `secrets.env` (`api` scope, at least Developer in the group); `check` verifies the token is its. It also signs the review's notes. Without an approver the review still runs and its notes say it could not approve. A refusal by GitLab is reported as it is, never shown as an approval.

**The fix loop.** An "unsure" verdict with no blocker and no failed build or tests is a question for people, not a fix: the MR is "could not confirm" with the reviewer's reason, nothing goes to the agent, and someone answers on the ticket. Findings of fit beside such a question still go to the agent, with the question marked as one for people, and nothing is approved. This holds even when the reviewer adds that the ticket is not met until the question is answered. So is any verdict reached while people changed what they asked for: when the ticket's text or comments, or what people wrote on the MRs, changed while the review ran, the MR and the ticket say it could not be confirmed and why, leave out its summary and findings, approve nothing, send nothing to the agent, and ask for `/review` again. So is a call for changes that does not name what it breaks and how it is reached: a blocker without `breaks` and `reached_by`, a finding of unknown severity, or a bare "changes" or "requirements not met". The MR note lists it, the MR is "could not confirm", and a person decides whether it is needed. When changes are needed, the runner sends the blockers that name both (with both), a failed build or tests and the findings of fit (with what each stands on, told to remove or align and add nothing, and to keep what a person decided), not the suggestions, to the agent that wrote the code as a round of its own, told to change only what each names, counted against `limits.max_review_rounds`; the note says "Sent to the agent to fix, round 1 of 3". When the reviewer was also unsure, its open question goes with them, marked as one for people that the agent must not settle in code. Once the agent has pushed new commits and the ticket is back in Code Review, the runner asks for the same review again in the first requester's name. This repeats until approval or until `review_agent.fix_rounds` (3) is used up; a round with no code change also ends it. Findings of fit alone send the MR back the same way, "changes are needed" with nothing broken, but only while rounds are left, and once per set of commits read against the same ticket and comments: a finding the author kept (the same merge request and target branch, file, line and basis, however it is worded) is not sent again until the code, the target branch or what people wrote changes, while a new one is. Once the rounds are used up, they no longer hold up the approval. They go back even when what people see was not looked at; the MR is then still not approved until someone looks. `fix_rounds: 0` turns the loop off. Asking again for commits that already have a final review returns that review, unless the ticket's text or comments, what people wrote on the MRs, or the review's rules have changed since.

**Merge requests people wrote.** On any ticket in Code Review the agent never worked on, a request reviews the merge requests of the group that the ticket links to, in its description or comments, each at the head GitLab has (forks included). The summary lists links it left out and why (a GitHub PR, another group, a second open MR of the same repository). The reviewer is told people wrote the code; there is no fix loop, and the note asks the author to change it and write `/review` again. Such a ticket is a task of kind `review` that nothing else touches; the runner lets go of it when it leaves Code Review or has no open MR, and requests older than `limits.continue_window` are ignored. Let go of in Code Review with every MR merged, the ticket gets the tags of `tracker.tags_on.merged` and is never moved. Queued for the agent later, it becomes an ordinary task.

**Switched off** while a review runs: the run finishes, nothing is posted or approved, and the ticket says so.
