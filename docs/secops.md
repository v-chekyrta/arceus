# Advisory triage

Off by default (`secops.enabled: false`). A company that keeps a register of security advisories (CVEs, GitHub advisories, vendor notices) needs someone to say, per advisory and per repository, whether a project is affected. With this on, the SecOps agent does that on command or on a schedule: it reads the project's code against the open advisories and gives a verdict per advisory and repository, with evidence; the runner keeps the verdicts in its reports and, when asked to, sends them to the register. The agent fixes nothing, and nothing goes through the issue tracker.

The register is a contract, like the tracker and the code host ([integrations.md](integrations.md#adding-an-advisory-register)). Built in is `files`, which needs no service: the advisories are a folder of [OSV](https://ossf.github.io/osv-schema/) records, and the verdicts go into an [OpenVEX](https://github.com/openvex/spec) document. A company's own register (a web service, a database) is a module of its own outside this repository, named by its path in `type`.

**The config.** The `secops:` section of `config.yaml`:

- `register` (required when enabled): which register, by `type`, and that provider's keys, checked like the `tracker` section. For `type: files`:
  - `advisories`: a folder with one OSV record per `.json` file, such as an export of the records that concern the project from an OSV database, or records of your own (OSV gives local ids the prefix `x_`). A record is open unless it has `withdrawn`; `modified` is what tells the runner it changed.
  - `verdicts` (optional): the OpenVEX v0.2.0 document the verdicts are written to, created on the first one. Without it the register is read-only: report only.
  - `author` (required with `verdicts`): the person or team the document names as its author.

  A register of your own may set `token_env`, the name of its secret in `secrets.env`: the runner reads it and makes every call itself; the agent's session never gets it.
- `instructions` (by default `~/arceus/data/secops/instructions.md`): optional notes on the team's stack, such as what is deployed where, which repositories are legacy and which versions are decided outside the code. The `runner` phase copies [secops-instructions.example.md](../config/secops-instructions.example.md) there once, as comments only. With nothing written, a triage run works from the code alone and reports in `bulava.report_language`; with notes, in their language. A run keeps the text it started with, for its brief and its closing review alike.
- `repos` and `skip`: which repositories are checked, and which never are, as patterns of their paths in the group (`architect` has the same). A `repo:path` pattern in `skip` names paths the agent is told not to cite.
- `post` (`false`): with `false` the verdicts stay in the run's report; with `true` they go to the register too. With a register that takes none (`files` without `verdicts`), `arceus-runner check` refuses `post: true`, and a run sends nothing and says why.
- `slack` (`false`): with `false` the project's channel hears nothing of these runs, neither the start nor the result. The events are in `events.jsonl` either way.
- `schedule`, `timeout` (4 h), `reports`, and `address:port` (127.0.0.1:3302) for the report pages while the web console is off.

`arceus-runner check` says whether a run can start: the notes can be read, a secret the register names is in `secrets.env`, and the register's own checks: it can be reached, its credentials are good for reading (and for receiving with `post`), and it covers the code host's group. For `files`: how many open advisories the folder holds, which files are not usable OSV records (a run leaves each out and its report names it, so the run is only partly checked), and, with `post`, whether the document can be read and its folder written. `arceus-runner run` does not ask the register: a register that is down keeps no ticket waiting.

**How a run goes.** `arceus-runner secops run` queues one; `secops status` and `secops stop [n]` work as for architecture reviews ([architect.md](architect.md)), and so does the schedule. A run is the Bulava task `secops-<n>` and holds the shared workspace like a test run, every repository on a local branch `arceus-secops/<n>` at its default branch. When the run is prepared, the runner reads every open advisory from the register, each one whole. With none open, the run ends without the agent as *no open advisory*, which costs no Claude time. A register that does not answer (a connection error, a timeout, a 5xx) is tried again on the following passes for half an hour from when the run was queued; the run waits as queued meanwhile, and new tickets wait behind it, at most that long. One that refuses, fails in another way (for `files`: a folder that cannot be read, or more than 5,000 records), or still does not answer after that ends the run as *did not finish*, saying why, without the agent: a run never gives a verdict it could not ground. The next scheduled run tries again.

**What the agent is told.** It is a security reviewer of this project's code: it reads code, changes nothing, asks nobody and cannot post anywhere. Each advisory's title, facts and text come from outside, so they are screened ([security.md](security.md)) as the agent would get them, once per text; one the screen does not clear, or cannot read at the time, is left out and named in the report. When it clears none, there is no agent: the run ends as *did not finish*, saying so. The rest go into `advisories.json` in the run's folder, rather than into the brief, which is one command-line argument the system caps at 128 KB. Each comes with its id, which the agent names it by, exactly as given (a number or a string), its facts as the register gives them (for `files`: the aliases, the severity scores and words, the affected packages with their version ranges and listed versions, the fixed versions and the references), its text, and the agent's earlier verdicts on it, its latest per repository whether `post` was on or off: what the last finished run kept, and, for a repository that run did not judge, what was last sent to the register. It checks them again, changing a word only when its evidence says what is different (the code, the advisory, a mistake in the earlier evidence, or the team's notes on its stack, naming what they say), and giving a repository that had a verdict one again (`fixed` or `not_affected` when the component is gone). The brief lists the repositories to check, each at the commit to read, and the team's notes. For each advisory the agent finds the repositories that carry the product or component (ship, pin, build or deploy it) and gives each one of four words:

- `affected`: it pins or ships an affected version or configuration;
- `fixed`: it carried the problem and now carries the fixed version or the patch;
- `not_affected`: the component is there, but its version, configuration or use is outside what the advisory describes;
- `needs_review`: the component is there, but what decides the answer is not in the repository (a setting at run time, a package on a host, the version actually deployed). This, never a guess.

A repository that does not carry the component, and had no verdict before, gets none, and so does one the team's notes leave out (they may say what counts as carrying it), named with the notes' rule in the advisory's line in `checked`. It writes `verdicts.json`: a short summary, a line in `checked` for every advisory it was given, and the verdicts with their evidence (at most what the register takes: 4,000 characters for `files`) and their files and lines. Before the run ends, Codex reviews that report by the runner's criteria (`REPORT_CRITERIA` in `secops.py`): the evidence supports the word, every reference is real, `needs_review` instead of a guess, no advisory silently dropped, nothing resting on a rule the notes do not contain, at most three rounds. It reads the team's notes from `notes.md`, which the runner writes beside `advisories.json` in the run's folder of the workspace (the engine gives its reviewer only the first 8,000 bytes of a criteria file). The notes are the project's own rules for judging its stack; they can excuse a repository left out as above, and nothing else: every verdict given still needs its evidence and real references, every advisory its line in `checked`, every earlier verdict a successor. When the agent is done, the runner checks `notes.md`: one that is there and is not what it wrote (in a run without notes, one with anything in it) may have had the review judge by rules the team did not write, and none of the run's verdicts are sent; one that is gone left the review the runner's criteria alone, the stricter case, and holds nothing back. A report it still objects to is shown with the objections, and its verdicts are not sent. The review reads at most 60,000 characters of the file, so the agent keeps it under 40 KB; a `verdicts.json` larger than 60,000 bytes was not reviewed to its end, and none of its verdicts are sent.

**The report.** The runner reads `verdicts.json` defensively: the advisory must be one the agent was given, the repository one it checks, the word one of the four, one verdict per advisory and repository, and every file and line is checked against the commit read. A verdict none of whose references exist is left out; `needs_review` may name none. Everything left out is named, and an advisory missing from `checked` is shown as not accounted for. The outcome is the runner's, never the agent's: *nothing needs attention*; *something does* (`affected` or `needs_review`); *partly checked* (advisories not accounted for, or left out, or part of the report left out); *no open advisory*; *did not finish*; *stopped*. Each run gets `report.html` and `result.json` under `reports`: per advisory its identifiers and severity, linked to its page when the register gives one (for `files`, the record's first `ADVISORY` or `WEB` reference), the verdicts by repository with their evidence and links into the code at the commit read, and whether each was sent, already on the register, or refused. With the web console on, they are read in its **Advisory triage** section (`public_url` + `/secops/`, [console.md](console.md#advisory-triage)), and the runner serves no page of them; a `reports` folder outside the data folder is mounted into the console's container by `setup.sh`, so run it after moving the folder. With the console off, the runner serves them on `127.0.0.1:3302` (`ssh -L 3302:127.0.0.1:3302 <user>@<vm>`, then `http://localhost:3302/`).

**What is sent.** With `post: true`, once a run that finished and whose report its closing review read whole and passed is over, each verdict goes to the register, naming its advisory by the register's id and its repository by its path in the group, the group, its address on the code host and the commit read. The runner keeps what it sent in `runner.db` (`advisory_verdicts`): the same verdict on an advisory whose content has not changed since is not sent again. Each verdict's row is written before it is sent and settled after; if the answer was lost (a crash, a timeout), the runner asks the register for the repository's latest verdict on the advisory before sending it again, so nothing is sent twice. A refusal is kept with the register's words and shown in the report, and the rest go on. While the register does not answer, the run waits after the workspace is put back and tries again on every pass for an hour; then the report goes out saying which verdicts were not sent. With `post: false` nothing is sent and the report says so, and so it is for a run under way when advisory triage is switched off.

With `files`, sending is writing: each verdict is a new statement appended to the OpenVEX document, which is rewritten whole and replaced in one step, so a reader never sees half of it. The statement names the vulnerability by the advisory's id with its aliases, the product by the repository's address on the code host, and the status by the verdict (`needs_review` is `under_investigation`); the evidence and the commit read are its `status_notes`. `not_affected` carries the evidence as its `impact_statement` and `affected` an `action_statement` (the fixed versions the record names, or a pointer to the advisory), because the specification asks for them. The document's `version` goes up by one with each statement, and its `timestamp`, `last_updated`, `author` and `tooling` are set again; a statement that took its time from the document keeps it as its own. A repository's latest verdict on an advisory is its last statement there. A document that is not OpenVEX v0.2.0 is never written over: the verdicts wait, as for a register that does not answer. The runner's own record decides what is sent, not the document: a verdict already written is not written again until its word or the advisory changes, also when the document was deleted or replaced meanwhile. To have every verdict written again, empty that record while no triage run is under way (`sqlite3 ~/arceus/data/runner.db "DELETE FROM advisory_verdicts"`, at `paths.db`); the next run writes all of its verdicts.

**Slack and Grafana.** Only with `slack: true`, the channel hears when a triage run starts (and whether the schedule started it) and how it ended: the outcome, the agent's short summary, the counts by word, how many verdicts were sent, and the report's link. On **Arceus · now** the agent shows as *Working* and the run is listed as `secops-<n>`.

**Cost.** One Claude session per triage run, up to `timeout`, and Codex's review of the report, from the same subscriptions as tickets. Each advisory text is screened once by the classifier (`claude -p`, `security.model`) the first time it is seen, and again only when it changes. The register is read once per run, sent one verdict at a time, and asked once more for a verdict whose answer was lost.

**Not in this change.** A register reached over HTTP of any kind: a company's own register is a module outside this repository ([integrations.md](integrations.md#adding-an-advisory-register)). Starting or stopping a run and editing the notes in the web console, and a role for advisory triage there (the console only reads the runs and their reports; its settings form shows the section, with `register` and the file paths locked); a check by the runner itself that every earlier verdict has a successor, or that a repository the notes leave out is named in `checked` (the closing review holds the agent to both); a check that `advisories.json`, which the closing review reads too, is still what the runner wrote (only `notes.md` is checked); skipping advisories whose verdict is settled (every open advisory is read again on every run); Grafana dashboards and metrics of their own; a second opinion of the runner's own on the verdicts; anything on tickets; fixing what is found.
