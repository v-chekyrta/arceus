# How a task goes in `live`

## Taking a ticket

1. Someone in `allowed_users` puts the `agent` tag on a ticket in the queued state. The tag's author is read from the ticket's history; a tag from anyone else gets one comment and is not taken.
2. The runner takes one task at a time. The ticket as it is at that moment (description, people's comments oldest first with author and time, files attached to it and to its comments) first goes through the [security screen](security.md); a held ticket is not claimed and its workspace is not touched.
3. **The workspace.** Tickets do not name a repository: the agent gets every repository of the code host's group (`code_host.group` on GitLab) except `exclude_repos`. The runner clones or fetches each, runs `night-shift trust` and `mcp-decide skip` in it once, creates the task branch from the default branch in every one and hands them all to the agent as writable (`SUPERVISOR_EXTRA_DIRS_FILE`). A repository with uncommitted changes stops the start.
   - The session starts in the workspace folder itself. Bulava needs a git project, so the folder is a small local repository of the runner's: a `.gitignore` that ignores every clone, and an `AGENTS.md` (read through `CLAUDE.md`) that says what the folder is and lists the repositories, followed by the project's notes ([agent-instructions.md](agent-instructions.md)). It has no remote and is never published; the next task starts from the runner's version again.
4. The ticket gets In Progress, the bot as assignee and a comment, and `dispatch.sh` starts the work on branch `agent/<KEY>-<slug>`. Follow-ups get the same repositories.

## Following the task

The task is reconciled with `night-shift task show` every `poll_local`:

- **`waiting_review` with `review: passed`.** MRs are opened only where the agent changed something (`reviewed_sha != base_sha`). Each repository in `receipt.repos` is checked first: branch, clean tree, `HEAD == reviewed_sha`, part of the group, `base_sha` on the default branch (otherwise the commits below it were never reviewed). If any check fails, nothing is pushed. Otherwise `reviewed_sha:refs/heads/<branch>` is pushed without force (unless the host already has exactly that commit) and the remote SHA compared afterwards. A branch that already holds commits on top of the reviewed one is left alone, with no MR and a note on the ticket. Then the MR is created or reused, the ticket gets the links and moves to Code Review.
- **`needs_input` / `blocked`.** The question and its options go to the ticket (with `state_reason: spec_conflict`, Bulava's own question: the review disputed something the task decided in so many words, and the task's author picks between keeping the task as written and changing it; its quote of the review goes through the same redaction as other review text), mentioning the tag's author, with the `agent-needs-input` tag. A run that stopped without a question in words gets a comment that says it waits for a person, what is not published, what the agent named as needed (its `blocker` findings), and then its whole summary. What is not published is said as it stands: before the first MR, nothing yet, with the branch and commits kept; in a later round, only that round's changes, with the links of the task's MRs, which stay as they were. Nothing the agent wrote is cut: a long text goes as several comments in order ("Part 1 of 3"), and the screenshots it left go with the last one. The same holds for the result of a run with no code changes and for the details of a failure. The first comment after it from someone in `allowed_users` goes to the agent (`worker-send --answers`); an answer that is only an option's number goes with the option's words, since the agent's brief has the question without its options. Without an answer: a reminder after `needs_input_reminder`, failure after `needs_input_fail_after`.
- **The agent changed nothing, saying nothing needs changing.** On a ticket with no merge request yet, an attempt that declared `succeeded_no_change` with every repository clean and still at its base is not a failure. Bulava reviews no such claim and banks it as `debt`, so the runner puts it to a person as a question with the `agent-needs-input` tag: the agent's reasons, and the two ways out. Closing the ticket accepts the conclusion: once the tracker counts the ticket as resolved (YouTrack sets `resolved` in the states the project marks so), the task ends as `done` ("no code changes"), the `agent-needs-input` tag comes off and nothing is published. Moving the ticket to another open state, or leaving it with no state, is not an answer: the task keeps waiting. A comment from someone in `allowed_users` while the ticket is open sends the agent back to work on the same branch, as with any answer, and whatever it changes is reviewed before anything is published; a comment on a ticket already closed is not sent. This question has no deadline: after `needs_input_reminder` it gets one reminder, and it never fails on its own. If the branch has commits an earlier attempt left that no review passed, it stays a failure (below). The runner keeps the question whole with the task, so the console's task page shows it as the ticket got it.
- **`failed`, `needs-user`, when the reviewers stopped the work for a person.** The review gate's last entry in the attempt's `runs/<run_id>/reports/blocked.md` (under `bulava_state`) is its own `— BLOCKED`: then this is a question, not a failure. The ticket gets what the reviewers asked (with a review team, each member that stopped it, under its name), what is not published (as above: nothing yet, or this round's changes beside the open MRs), and the agent's summary, with the `agent-needs-input` tag. The answer goes on as above, as a new attempt that is reviewed again before anything is published; after the MRs were opened, its fix goes to the same MRs. The same holds when the agent filed a `blocker` finding (the receipt's `review_why` starts `worker blocker finding:`), which Bulava also parks as `needs-user`: the agent waits for a person to give or do something, so the ticket gets the stop-without-a-question comment above with what it needs, and a reply takes the work on. The note counts only for the run of the receipt when it is the last attempt's; the gate's other entries there (a reviewer it could not reach, rounds without progress) and every other `needs-user` stay failures.
- **`done`.** The ticket gets a comment with the result; nothing to push.
- **`failed`, `debt`, a dirty tree, or a timeout.** An attempt fails as "the agent hung" after `attempt_timeout` (8 h) with no sign of activity: no engine step of its own (Bulava repeats the step every minute while a long check runs) and nothing written to the agent's transcript. The runner reads the attempt's files right before it decides, so a sign of life since its last look, or after a restart, is never missed. However busy it is, an attempt with no verdict after `attempt_ceiling` (24 h) of time it could work fails as "the attempt ran out of time": the time it waits for a usage window, as Bulava records it for that attempt (`paused-for-limit.json` with its dispatch id and a usage reason, written by its watchdog and review gate; the same file parking an unreachable reviewer is no such wait), neither counts toward it nor starts it again, and is kept with the task across a restart, beginning when Bulava recorded it (the marker's `recorded_at`) and ending when Bulava took it off (`pause-last.json`), not when a runner that was down first or last saw it (a pause that began and ended while the runner was down leaves no record of its start or its attempt in Bulava 1.20.9, so it counts as working time); silence counts again from the end of a pause; a used-up limit alone pauses nothing, so an attempt that goes on working meanwhile (a final check still beating, background agents) is not paused. Both reasons name where the attempt was, as far as is known: its last step, the review round and the review's open items (the task's review list in Bulava). The ticket gets the reason and the `agent-failed` tag. The reason names the stop Bulava's receipt names: the reviewer could not be reached (the work was not reviewed); the agent left work uncommitted after being asked to commit it (with the repositories); the agent reported it could not finish; the project's automated checks kept failing whatever Codex said, until the rounds ran out (with each failed check by a label, `check 1`, `check 2`, and its exit code, read from the run's evidence, and where the work is kept; a check's name, command, note and log can hold a token or an internal address, so they stay in the run's evidence on the server, and the event log, which goes on to Loki, has only `verifier_gap` with the label's number, the check's status, exit code and run); the review kept finding the same problems with no progress between rounds, or every fix brought a new blocking problem, or still found some when its rounds ran out (with those findings, leaving out what the review does not block on); the review accepted the work but the heavy checks registered with `add-check --final` did not pass or left nothing readable; and, for a ticket with no merge request yet whose last attempt said nothing more needed changing, that commits an earlier attempt made were never reviewed (with where they are), so nothing was published. Any other stop of the review says that the review stopped the work, with the agent's summary. `review_why` itself never goes on the ticket whole: it can hold a CLI's output and paths on the server. What the attempt left uncommitted becomes a `WIP [KEY]` commit on the task branch, reviewed with the rest before anything is published. While Bulava records the attempt as paused for a usage window, the attempt's clock stands still.
- **`running` with no live session** (for example after a reboot): continued with `worker-send --relation continue`.

**`/continue`.** A comment from someone in `allowed_users` that starts with `/continue`, within `continue_window` (14 days), resumes a failed task: a new attempt with the same goal, branches and commits, plus the comment's text (`worker-send --relation continue`). It is journaled, sent once, goes before new tickets and survives a restart; the bot puts 👀 on the comment when it is taken. The `agent-failed` tag comes off, the ticket returns to In Progress, and the review and CI budgets start again. It also resumes a task stopped because people closed every MR. If Bulava no longer has the task, it starts again from the ticket on the same branches. Other comments on a failed ticket wake nothing.

**Tags.** The ticket's tags, the runner's own left out, go to the agent with the summary and the description, and to the code reviewer of `/review`. A follow-up (`/continue`, an answer) says so when people changed them since. `tracker.platforms` maps a tag that names a platform to its repositories: the brief then names those repositories, and the work is not published while a tagged platform has no change in any of them. The first time it goes back to the agent once with what is missing; after that the task fails, and people either `/continue` it or take the tag off first. `doctor` fails a platform whose repository the agent does not get.

**Research tickets** carry `agent-research` (`tracker.tags.research`) next to `agent`; who may start one is still decided by `agent`. The agent changes nothing and writes its answer to `.arceus/notes/<KEY>/answer-<run>.md`, a new file per run. The runner keeps a copy in `data/tasks/<KEY>/` and posts it on the ticket whole, in several comments when long; no push, no MR. A missing or unreadable answer (a symlink, over 512 KB) is asked for once, then the task fails. The ticket then moves to `tracker.states.answered` (Code Review; `null` leaves it In Progress), with the tags of `tracker.tags_on.answered`. A `/continue` with a follow-up question gets a new answer; to have the answer implemented, queue a new ticket without the research tag.

**Progress on the ticket.** The comment that started the attempt now running (the claim, or the comment for a `/continue`) grows a Progress section that the runner edits in place while the task runs (ticket_progress.py): what happens now (preparing the brief, the agent at work, the build, Codex's review, a pause for a usage limit, a question, the merge requests), when it started, the agent's latest actions (its own one-line descriptions and workspace paths, shown as code), the steps so far and the merge requests. A new step or state is written at the next look; only new actions, at most every `schedule.progress_comment_every`; an unchanged text never. The edit is not silent, which is why it is held to that. The comment says how the task ended once and is then left alone. A `/continue` moves the section into the runner's "picking this up again" comment, the newest on the ticket, so it sits where people are reading; the comment it leaves is put back as it reads without the section (a person's edit above it stays), retried until the tracker takes it. A removed comment is not written to again. `tracker.progress_comment: false` turns it off.

## After the MR

On each poll of the code host the runner watches every MR of the task for:

- review notes by people that mention the bot (`@` and `code_host.bot_user`), in every discussion, late replies in old threads included. Anyone with access to the repository may ask the agent this way; the text goes through the security screen. Notes without the mention, the bot's own and the host's system notes wake nothing;
  a comment on the ticket brings them along, though: every one that goes to the agent (review, an answer to its question, a `/continue`) carries the threads people left unresolved on the task's open MRs, under "Open discussions on the merge requests", so "see the discussions on the MR" can be followed (the agent cannot read the code host itself). They are context there, not requests, and the runner posts no answers in them; threads already addressed to the agent in the round, resolved ones, and the runner's and the code review's own notes are left out;
- the head pipeline: a failure of the commit the runner published is sent with the failed jobs and the end of their logs; a running, cancelled or older pipeline is not, and one that turns green or is replaced before it is sent is dropped;
- a conflict the code host has confirmed (GitLab `detailed_merge_status: conflict`; `checking` does not count);
- ticket comments by people in `allowed_users`, except `/review` and `/security-allow` / `/security-reject`, which are the runner's.

Signals are stored once. When `review_debounce` has passed since the newest one, they go to the agent as one follow-up of the same Bulava task (`worker-send --relation continue --source mr|ci|youtrack`), the ticket returns to In Progress, and Codex reviews the fix against the original goal. Fixes for open MRs go before new tickets.

- **Threads.** Each thread goes to the agent whole, the new notes marked. The agent decides per thread whether it asks for a code change or only an answer, and writes one answer per thread to `.arceus/replies/<ticket key>/<round>.json`; for the reasons behind its choices it reads its own `.arceus/notes/<ticket key>/decisions.md`. The runner pushes the new reviewed commit (fast-forward, never force), rewrites the MR description and posts each answer in its thread, with the commit where code changed. A reply that cannot be delivered, because its thread is not to be found in the merge request's discussions or by its id, or because the code host answers 404 to reading them or to the post, waits (`reply_waits`): it stays pending and is tried again on every tick while the task and its other replies go on to Code Review, and goes out once. The pending reply names the merge request it was written for, so it still goes there after a later round drops that merge request from the task or opens another one; a reply journaled before the runner named it gets it from its note's link, and waits, saying why, when the link does not tell it. The notes of a thread count as answered only once its one reply is there. Nothing is posted into a thread the runner cannot see, and a reply is never dropped, since a 404 does not tell a deleted thread from one the bot may not see; a thread people deleted keeps its reply pending for good. Other failures (5xx, timeouts) keep the task publishing and are retried on the next tick. Whatever they ask again in a new thread is the next round. Threads are left for people to resolve. A round that changed no code only posts the answers; a thread the agent left unanswered gets its overall explanation.
- **People's commits.** Before each follow-up every repository is put back on the task branch and caught up with what people pushed to the MR; a push while the agent is fixing is merged in on the next round.
- **Merge once green (`tracker.tags.merge`, `agent-merge`).** With this tag next to the queue tag, put on by someone in `allowed_users` (the tracker's history says who), every MR the runner publishes is set to merge when its pipeline passes, with the reviewed commit's sha: GitLab keeps that sha and checks it again when it merges, so a later push is never merged. Only into the repository's default branch and only while the MR head is still the reviewed commit; never a release branch or a tag. Where the default branch deploys dev by itself, that is "deploy it to dev". The merges are journaled before the ticket moves to Code Review, so a crash or an unwell code host only delays them; a refusal (a closed MR, another target, new commits, conflicts, no right to merge) is final and said on the ticket. The tag from anyone else merges nothing, and the ticket says why.
- **Closing.** The task is **done** when all its MRs are merged; the ticket then moves to `tracker.states.merged` (`Testing`; `null` leaves it in Code Review; `check` warns when the board has no such state) unless a person already moved it. The tags of `tracker.tags_on.merged` (`add`, `remove`; none by default) are set then too, with or without that move, so a board that keeps merged tickets in Code Review can mark them (`ready for dev`). An MR a person closes while others are open goes to the agent, which takes that repository's changes out, and the MR leaves the task. When people close every MR and merge none, the task stops (`stopped`, no failure tag) and `/continue` can pick it up, opening a new MR. Some merged and the rest closed is done, without the `tags_on.merged` tags: they need every MR merged. A ticket moved past Code Review by hand stops the task for good, and gets no `tags_on` tags. The runner sees only its own steps: a move people make on the board sets no tags.
- **Budgets**, kept across restarts: `max_review_rounds` (rounds that published code), `max_review_answers` (rounds answered without a code change), `max_ci_fix_attempts` (CI repairs in a row, reset by a green pipeline). When one runs out the task fails with one comment saying why.

## Who opens and describes the MR

The runner. Bulava's server profile refuses `git push` inside a run, so the agent only commits. The runner writes the code host bot's credentials (`CodeHost.git_auth`) to `~/.git-credentials` for that host only, so plain `git fetch` and `pull` work for the agent too and the token is never in a URL, a command line or `.git/config`. If the engine later lets the agent push, the runner still checks after the review that the host holds exactly the reviewed commit.

The MR description has the ticket with a link; **What was done**, the agent's own run summary; **Commits** since the base; **Checks**, which commit passed review (no model names or round counters); and the other MRs of the same task. It is rewritten after every round to match the branch.

## Doing nothing twice

Comments go through a journal in SQLite and carry an `[arceus:…]` marker; dispatches and follow-ups have stable message ids; a push is compared with the remote first and an MR is looked up before it is created. GitLab learns of a pushed branch a moment after the push, so an MR it refuses with `source_branch does not exist` is asked for again up to three times, 1, 2 and 4 seconds apart; past that the next tick publishes it. After a crash the next tick finishes what is missing and duplicates nothing.
