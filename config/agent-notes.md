## Arceus server notes

You run unattended on the project's server, fed tickets by the Arceus runner. These notes come from the team that runs the server.

**The workspace** is the folder your session starts in: it holds the project's repositories, one folder each, and an `AGENTS.md` that gives its absolute path and lists the repositories. Below, `<workspace>` stands for that absolute path and `<ticket key>` for the ticket you work on (for example `ABC-12`). Wherever a path is asked for, write the real one out in full.

- **Language.** Commit messages, your run summary (it becomes the merge request description) and anything that ends up in the merge requests or on the ticket are written in English, whatever language the ticket or a comment uses.
- **The run summary is the merge request's "What was done".** Each time you declare the outcome, describe the whole change on the task branch as a reviewer meets it: what the ticket asked for and how you did it, the decisions that shape it, how you checked it. Not only what the last round fixed: a summary such as "Round 3: make verify no longer writes into the working copy" replaces the description of the feature on the MR. A round's fix goes in a sentence at the end, if at all.
- **Dev servers.** Start long-running processes (`manage.py runserver`, `npm run dev`, a static file server) with the Bash tool's `run_in_background`, not with `&` inside a command. Stop them by PID, or with a pattern that cannot match your own command line: `pkill -f "[m]anage.py runserver"`. A plain `pkill -f "manage.py runserver"` also matches the shell running it and kills your own command (exit code 143/144).
- **Screenshots.** Files the engine's tools save under `~/.claude/supervisor/reports/` can be opened with Read; look at them to check visual work.
- **Visual proof for reviewers.** When your change is something people see (a page, a component, an error screen, an email), leave proof of it for the merge request and the ticket. You cannot upload anything yourself; the runner does it when it publishes your work.
  - Put the files in the workspace's media folder for this ticket, `<workspace>/.arceus/media/<ticket key>/`. Never put them in a repository or commit them.
  - Next to them, write `media.json`: `{"items": [{"file": "404-desktop.png", "caption": "404 page, desktop", "repo": "web"}, {"file": "retry.webm", "caption": "503, then Retry recovers", "repo": "web"}]}`. `repo` is the repository the file belongs to, as `AGENTS.md` lists it (its MR gets it); without it, every MR of the ticket gets the file. Captions are short, plain English. Only listed files are uploaded.
  - Screenshots of every state you changed, at desktop (1440 px) and phone (390 px) width when the layout differs; a short recording (Playwright `recordVideo`, webm) when the point is an interaction: a click, a retry, a redirect. Take them from the real app (a dev server or a build), in a container like your checks, not from a mock.
  - `png`, `jpg`, `gif`, `webp`, `webm` or `mp4`; at most 12 files, 25 MB each, 100 MB in all. `ffmpeg` is on the server for trimming a recording to the part that matters or shrinking one that is over the limit (`ffmpeg -i in.webm -ss 2 -t 8 -c:v libvpx-vp9 -b:v 0 -crf 40 out.webm`).
  - When a review round changes what is on screen, replace the files and update `media.json`; it is read again every time your work is published. Leave the folder alone for work nobody sees (a backend change, a config).
- **Taking a repository out of the task.** When a repository should no longer be part of the ticket (a reviewer or the ticket says so, or a person closed its merge request), undo your commits there with `git revert` on the task branch, so the branch has no difference from the default branch. Never reset or rewrite the branch: the runner does not force-push. When the work is published, the runner sees there is nothing left to merge in that repository: it pushes nothing there and closes its merge request if it is still open. You cannot close merge requests yourself. Do not keep changes in a repository whose merge request a person closed; if they belong elsewhere, move them.
- **Notes on your decisions.** Reviewers ask on the merge request why you chose one approach over another, often weeks later and in a session that does not remember the work. While you work on a ticket, keep `<workspace>/.arceus/notes/<ticket key>/decisions.md`: for each choice a reviewer could question, what you chose, what you considered instead, and why. A few lines each; add to it in later rounds. Never put it in a repository or commit it.
- **One verify entry point per repository you change.** The engine's verifier checks every repository the task changed. If none of your registered checks names that repository, it runs the repository's own entry point on this server's bare shell, in this order: an executable `verify.sh`, then `make verify`, then `make test`. The server has Docker, `git` and `node` but no project toolchains (`uv`, `pnpm`, `pylint`, `mypy`, …), so a plain `make test` here fails for reasons that have nothing to do with your change, and the work is not published. So, in every repository you change:
  - Make sure it has `make verify` (or `verify.sh` when there is no Makefile). If it exists, use it and update it when your change needs more; if not, add it in the same commit as your change.
  - It runs what the repository's CI runs on a merge request (lint, type checks, unit and backend tests), with the tools inside containers: the image CI uses, or an official one (`python:3.12`, `node:24`, `ghcr.io/astral-sh/uv`), plus the services CI starts (a database, Meilisearch). Mount the repository, keep files readable (see Containers), and cache dependencies in a named volume so a second run is fast. It must not check less than CI does.
  - It must finish in under 10 minutes on a warm cache. Long browser suites (full Playwright, visual baselines) stay out of it and are registered as checks of their own.
  - Run it yourself until it passes.
- **The code host's CI runs after you.** You cannot push, so no pipeline exists for your newest commit while you work: the runner pushes it once the review passes, and a red pipeline then comes back to you as a follow-up with the failed jobs and their logs. When a ticket asks for "CI green", running every CI job locally in its image (`make verify` above) is what you can prove; say so in the summary. Never file a blocker or stop for a person because the code host's pipeline of an unpushed commit cannot be seen.
- **Checks you register.** `add-check` runs its command in the folder the session started in (the workspace with all the repositories), not in the repository you are standing in. Name the repository by its absolute path, written out literally (no `$PWD`, no relative `cd`): that is how the verifier knows the check covers that repository and does not run the bare-shell fallback above. Register each changed repository's entry point, for a repository `web` in a workspace at `/home/ai/arceus/acme`: `add-check "web: make verify" -- make -C /home/ai/arceus/acme/web verify`, and further checks the same way: `add-check "web: error-pages e2e" -- bash -c "cd /home/ai/arceus/acme/web/e2e && npx playwright test tests/features/error-pages.spec.ts"`. At most 10 checks, each under 10 minutes, all of them under 25.
- **Containers.** The workspace is mounted into containers that run as other users. Keep files you create world-readable (mode 644, directories 755); do not chmod them to 600.
- **What you leave behind.** The runner cleans up after tasks that are over. It removes only what it can tie to your ticket, so make that easy:
  - A container, volume, network or image you create outside a repository's own compose file: add `--label arceus.task=<ticket key>` (`docker build --label …` for an image), and `--rm` to one-off containers. A volume of test data goes only with that label; named volumes without it are kept as dependency caches.
  - Test data goes in a container or volume of its own, never in the project's shared dev stack.
  - Before you declare the outcome, stop the dev servers you started and remove the containers you no longer need. The runner never removes a compose service's container without your label (it cannot tell a test stack from the dev stack), so take down a compose stack you started only for checks yourself; leave the dev stack running.
  - Uncommitted files left in a repository after the task is over are moved to `git stash` (message `arceus-cleanup …`), not deleted.
