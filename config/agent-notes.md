## Arceus server notes

You run unattended on the project's server, fed tickets by the Arceus runner. These notes come from the team that runs the server.

**The workspace** is the folder your session starts in: one folder per repository of the project, and an `AGENTS.md` with its absolute path and the list of repositories. Below, `<workspace>` is that absolute path and `<ticket key>` the ticket (for example `ABC-12`); wherever a path is asked for, write the real one out in full.

- **Language.** Commit messages, the run summary and anything that reaches the merge requests or the ticket are in English, whatever language the ticket uses.
- **The run summary is the merge request's "What was done".** Each time you declare the outcome, describe the whole change on the task branch as a reviewer meets it (what was asked, how you did it, the decisions that shape it, how you checked it), not only what the last round fixed: "Round 3: make verify no longer writes into the working copy" would replace the feature's description on the MR.
  - One sentence with the result, then `### Changes` and `### How it was checked`, short bullets, one fact each; `### Limitations` only for what a reviewer must know before merging. Headings are `###`. No work history, retold ticket or commit list. Local checks are named as local, not CI.
  - Write it to `<workspace>/.arceus/notes/<ticket key>/summary.md` and pass `"$(cat <that file>)"` to the outcome command, so line breaks survive and backticks are not run by the shell.
- **Research tickets** end with "How this ticket is handled". For them nothing below about merge requests, commits and visual proof applies: change nothing, write the answer to the file the ticket names, and make the summary a short version of that answer.
- **Dev servers.** Start long-running processes (`manage.py runserver`, `npm run dev`) with the Bash tool's `run_in_background`, not with `&`. Stop them by PID or with a pattern that cannot match your own command line: `pkill -f "[m]anage.py runserver"`; without the brackets it kills your own shell (exit 143/144).
- **Screenshots** the engine's tools save under `~/.claude/supervisor/reports/` can be opened with Read.
- **Visual proof.** When your change is something people see (a page, a component, an error screen, an email), leave proof for the merge request and the ticket; the runner uploads it when it publishes your work.
  - Files go in `<workspace>/.arceus/media/<ticket key>/`, never in a repository. Beside them, `media.json`: `{"items": [{"file": "404-desktop.png", "caption": "404 page, desktop", "repo": "web"}, {"file": "retry.webm", "caption": "503, then Retry recovers", "repo": "web"}]}`. `repo` is the repository as `AGENTS.md` lists it (its MR gets the file; without it every MR does). Captions are short, plain English. Only listed files are uploaded.
  - Screenshots of every state you changed, at 1440 px and 390 px width when the layout differs; a short recording (Playwright `recordVideo`, webm) when the point is an interaction. Take them from the real app running in a container, not from a mock.
  - `png`, `jpg`, `gif`, `webp`, `webm` or `mp4`; at most 12 files, 25 MB each, 100 MB in all. Trim or shrink a recording with `ffmpeg -i in.webm -ss 2 -t 8 -c:v libvpx-vp9 -b:v 0 -crf 40 out.webm`.
  - When a review round changes what is on screen, replace the files and update `media.json`. Work nobody sees (backend, config) needs none.
- **Taking a repository out of the task** (a reviewer or the ticket says so, or a person closed its merge request): `git revert` your commits there on the task branch until it has no difference from the default branch; never reset the branch. The runner then pushes nothing there and closes its MR. Move changes that belong elsewhere.
- **Conflicts with the target branch: rebase, never merge.** `git fetch origin && git rebase origin/<target>`, resolve, `git rebase --continue` until it is done; never leave it half done. You do not push; the runner republishes the branch without losing commits people pushed.
- **Notes on your decisions.** Reviewers ask weeks later, in a session that does not remember the work, why you chose one approach over another. Keep `<workspace>/.arceus/notes/<ticket key>/decisions.md`: for each choice a reviewer could question, what you chose, what else you considered and why, a few lines each, added to in later rounds. Never commit it.
- **Every repository you change needs one verify entry point, registered as a check.**
  - The server has Docker, `git` and `node` but no project toolchains (`uv`, `pnpm`, `pylint`, `mypy`, …). A changed repository that no registered check names gets `verify.sh`, `make verify` or `make test` run on that bare shell, which fails for reasons unrelated to your change, and the work is not published.
  - So the repository has `make verify` (or `verify.sh` without a Makefile): use and extend the existing one, or add it in the same commit as your change. It runs what CI runs on a merge request (lint, type checks, unit and backend tests) inside containers: CI's image or an official one (`python:3.12`, `node:24`, `ghcr.io/astral-sh/uv`), plus the services CI starts, the repository mounted, dependencies cached in a named volume. Never less than CI; under 10 minutes on a warm cache. Long browser suites are checks of their own. Run it until it passes.
  - `add-check` runs in the workspace, not in the repository you stand in, so name the repository by its absolute path written out literally (no `$PWD`, no relative `cd`). For `web` in `/home/ai/arceus/acme`: `add-check "web: make verify" -- make -C /home/ai/arceus/acme/web verify`; `add-check "web: error-pages e2e" -- bash -c "cd /home/ai/arceus/acme/web/e2e && npx playwright test tests/features/error-pages.spec.ts"`. At most 10 checks, each under 10 minutes, all under 25.
  - Every registered check must pass: one that fails stops the work from being published. A new check replaces an old one only when the name or the command is the same; otherwise both stay. To change a check, `add-check --remove "<old name>"` first, and run `add-check --list` before you declare the outcome. Never narrow a check (fewer jobs, deselected tests) to get past a failure: fix it. When the same failure happens on the target branch in the same environment, the test is broken there: fix the test or its setup in a commit of its own and name it in the summary; declare `blocked` with both runs' output only when that needs a change outside the tests.
- **The code host's CI runs after you.** No pipeline exists for your newest commit while you work; a red one comes back later as a follow-up with the failed jobs' logs. When a ticket asks for "CI green", running every CI job locally in its image is what you can prove; say so in the summary. Never stop or file a blocker because an unpushed commit has no pipeline.
- **What you leave behind.** The runner cleans up only what it can tie to your ticket.
  - Containers run as other users: keep files you create world-readable (644, directories 755).
  - A container, volume, network or image you create outside a repository's compose file gets `--label arceus.task=<ticket key>` (`docker build --label …` for an image); one-off containers also `--rm`. Remove a container with `docker rm -f -v`: database images keep their data in anonymous volumes, and without `-v` those stay behind. Named volumes without the label are kept as caches.
  - Test data goes in a container or volume of its own, never in the project's shared dev stack.
  - While a task waits days for a review or an answer, the runner removes its networks, images and dev servers, and the containers and volumes you marked `--label arceus.disposable=true` (or ran with `--rm`). Mark what a script or a command makes again: a seeded test database, an app container, a build. Leave the mark off what is the only copy of something a reviewer may need, such as a reproduced bug's data. Your branch and `.arceus` notes always stay. A later round's message names what was removed: make it again before you use it.
  - Before you declare the outcome, stop the dev servers you started and take down containers and compose stacks you started only for checks; leave the dev stack running.
